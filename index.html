Basic Structural Modeling

Static Features, System Framework & Structural vs Behavioral Perspectives

Core Concept

Meaning of Structural Modeling

Structural modeling captures the static aspects of a software system. Unlike behavioral modeling which tracks activities and message flows over time, structural modeling represents the skeleton or physical fabric of the system: the things that exist (classes, interfaces, components, nodes) and how they are wired together.

It forms the system framework—the structural blueprint that provides the architectural foundation upon which dynamic behaviors and algorithms execute.

Key Subtopics & In-Depth Concepts

1. Static Features of a System

A software system's static features remain invariant across runtime execution flows:

  • Structural Entities (Nouns): Objects, Classes, Interfaces, Collaborations, Components, and Nodes.
  • Relationships: Associations, Generalizations, Dependencies, Realizations, and Aggregations.
  • Structural Properties: Attributes, data types, multiplicity constraints, visibility rules (public, private, protected), and component boundaries.
2. Structural Model and System Framework

In software architecture, the system framework is the persistent structural backbone. Think of a skyscraper: the steel beams, concrete floors, and elevator shafts are the structural model; the movement of elevators, human foot-traffic, and power grid flows are the behavioral model. Without a robust structural model, the software lacks cohesion and maintainability.

Types of Modeling

Structural, Behavioral & Architectural Modeling Dimensions

Taxonomy

The Three Modeling Dimensions in UML

UML provides three comprehensive perspectives to specify, visualize, and document software systems: Structural Modeling, Behavioral Modeling, and Architectural Modeling. A complete system model requires all three perspectives working synergistically.

Detailed Analysis of Modeling Types

1. Structural Modeling

Represents the static skeleton of software entities, their attributes, operations, and inter-connections.

  • Class Diagram: Types, inheritance, associations.
  • Component Diagram: Physical modules, libraries, JARs, APIs.
  • Deployment Diagram: Hardware nodes, network topologies, runtime placement.
  • Object Diagram: Runtime instance snapshots.
2. Behavioral Modeling

Represents the dynamic behavior, state transitions, message interactions, and control logic.

  • Activity Diagram: Step-by-step algorithms, business workflows, parallel forks/joins.
  • Interaction Diagrams: Sequence & Collaboration (Communication) diagrams showing message flows.
  • Use Case Diagram: High-level external user interactions and functional requirements.
  • State Machine Diagram: Event-driven lifecycle of reactive objects.
3. Architectural Modeling

Represents the global framework, physical distribution, packaging, and non-functional blueprints.

  • Overall System Framework: Blends structural components with deployment nodes.
  • Package Diagram: Organizes large enterprise codebases into layered subsystems and namespaces.
  • Cross-cutting Concerns: Security, scalability, network protocols, fault tolerance.

Class

Basic UML Element, Attributes, Operations & 3-Compartment Notation

Foundational Element

Meaning of Class in UML

A Class is a description of a set of objects that share the same attributes, operations, relationships, and semantics. In UML, a class is the central classifier used to represent software entities, domain concepts, or technical abstractions.

Key Subtopics & Syntax Specifications

1. Class as a Basic UML Element

In UML metamodel, a Class is represented as a solid-bordered rectangle divided into three standard compartments:

  1. Top Compartment (Name): Contains the class name. Centered, bold, starting with an uppercase letter (e.g., Student). Abstract classes are written in Italics or adorned with {abstract}.
  2. Middle Compartment (Attributes): Lists the data fields/properties holding the object's internal state.
  3. Bottom Compartment (Operations): Lists the functions/methods that define the object's behavior.
2. Class Attributes Syntax & Visibility

Full UML attribute specification syntax:

[visibility] name : type [multiplicity] [= default-value] [{property-string}]

Standard visibility indicators:

  • + Public: Accessible by any classifier in the system.
  • - Private: Accessible only within this class.
  • # Protected: Accessible within this class and its descendants (subclasses).
  • ~ Package: Accessible by any classifier within the same package.
3. Class Operations Syntax

Full UML operation specification syntax:

[visibility] name (parameter-list) : return-type [{property-string}]

Where each parameter has the form: direction name : type = default-value (directions: in, out, inout).

Relationships

Dependency, Association, Generalization, Inheritance & Aggregation

Structural Connectivity

Meaning of Relationship in UML

In object-oriented modeling, a Relationship is a semantic connection among model elements. Standalone classes provide little value; real-world systems emerge from how classes connect, collaborate, inherit, and depend on each other.

The Four Fundamental UML Relationships

1. Dependency (- - - ->)

A semantic connection where a change in the independent element affects the dependent element (a "uses-a" relationship). Example: A class operation that takes another class as a method parameter.

Notation: Dashed line with an open arrow pointing toward the independent provider.

2. Association (─────)

A structural relationship that specifies that objects of one class are connected to objects of another class. It indicates a permanent or semi-permanent link.

  • Role Names: Specify the role a class plays in the association.
  • Multiplicity: Specifies how many instances can connect (0..1, 1, *, 1..*).
  • Navigability: An arrow on one end shows directed association (can traverse A to B, but not B to A).
3. Generalization & Inheritance (─────▷)

A taxonomic relationship between a more general classifier (superclass) and a more specific classifier (subclass). The subclass inherits attributes, operations, and relationships of the superclass ("is-a" relationship).

Notation: Solid line with a hollow triangular arrowhead pointing to the parent class.

4. Aggregation & Composition (◇───── & ◆─────)

A specialized form of association representing a whole-part ("has-a") relationship:

  • Shared Aggregation (Weak): Hollow diamond (◇). The part can exist independently of the whole. (Example: College and Department, or Car and Wheel).
  • Composite Aggregation (Strong / Composition): Solid filled diamond (◆). The parts are strictly owned by the whole and die when the whole dies. (Example: Order and OrderLineItem, or Human and Brain).
Categorizing Real-World Relationships (Classic AKTU Problems)
Real-World Statement Relationship Category Justification
"A country has a capital city" Association (1 to 1) Peer structural connection between two distinct entities.
"A file contains records" Aggregation / Composition Whole-part relationship; records form the contents of a file.
"A student is a person" Generalization (is-a) Subclass specialization; Student inherits Person properties.
"A controller uses a printer service" Dependency (uses-a) Temporary reliance via method invocation without structural ownership.

Common Mechanisms

Specifications, Adornments, Common Divisions & Extensibility (Stereotypes, Tags, Constraints)

UML Architecture

The 4 Common Mechanisms of UML

To make the language simple, consistent, and endlessly scalable, the creators of UML (Booch, Rumbaugh, Jacobson) built four common mechanisms that apply uniformly across all diagrams.

Detailed Breakdown of Common Mechanisms

1. Specifications

Behind every graphical icon in UML lies a detailed textual specification. The graphic diagram provides the visual overview, while the underlying specification defines formal semantics, full type contracts, preconditions, and invariant expressions.

2. Adornments

Basic UML notations can be visually embellished with adornments. Examples include:

  • Visibility signs (+, -, #) added to attribute lines.
  • Multiplicities (1..*) adorning association ends.
  • Navigability arrowheads and role names.
3. Common Divisions

UML enforces two fundamental dichotomies across the entire system:

  • Division of Classifier vs. Instance: Classes, Components, and Nodes are classifiers (types); Objects, Component Instances, and Node Instances are concrete runtime manifestations.
  • Division of Interface vs. Implementation: An interface specifies what contract a service promises, while an implementation specifies how that contract is fulfilled.
4. Extensibility Mechanisms (Crucial for Exams)

UML is an open-ended modeling language. It can be tailored to any specialized domain (e.g. Real-time systems, Java Enterprise, Aerospace) using three built-in extensibility mechanisms:

Stereotypes <<name>>

Extends the UML vocabulary by creating new building blocks derived from existing ones.

Syntax: Enclosed in guillemets <<...>>.

Examples: <<interface>>, <<utility>>, <<entity>>, <<actor>>.

Tagged Values {tag=val}

Extends model elements by attaching new metadata or properties not present in standard UML.

Syntax: {name = value}

Examples: {version = "2.1"}, {author = "Lexon"}, {cost = "$500"}.

Constraints {rule}

Extends element semantics by introducing new rules or conditions that must evaluate to true.

Syntax: {boolean condition}

Examples: {age >= 18}, {ordered}, {read-only}, {xor}.

Diagrams

UML Diagram Classification, Structural, Behavioral & Architectural Views

Visual Blueprint

Purpose of UML Diagrams

A UML Diagram is the graphical presentation of a set of elements, most often rendered as a connected graph of vertices (things) and arcs (relationships). Diagrams provide human stakeholders and developers with accessible visual projections into the system model.

Classification of UML Diagrams

The Master Diagram Classification Hierarchy

Standard UML defines 14 official diagrams grouped under two fundamental branches:

Structural Diagrams (7)

Display the static organization of system elements:

  1. Class Diagram: Central blueprint of classes and associations.
  2. Object Diagram: Static runtime snapshots of instances.
  3. Component Diagram: Modular physical code/binary components.
  4. Deployment Diagram: Hardware network topology & artifact placement.
  5. Package Diagram: Hierarchical organization into namespaces.
  6. Composite Structure Diagram: Internal class decomposition & ports.
  7. Profile Diagram: Custom domain stereotypes and metamodels.
Behavioral Diagrams (7)

Display dynamic behavioral changes and message interactions:

  1. Use Case Diagram: External actor interactions & requirements.
  2. Activity Diagram: Step-by-step control & object flows.
  3. State Machine Diagram: Lifecycle states of reactive entities.
  4. Sequence Diagram: Chronological, time-ordered messaging.
  5. Communication (Collaboration) Diagram: Structural link messaging.
  6. Timing Diagram: Exact real-time duration waveforms.
  7. Interaction Overview Diagram: Activity diagram containing sequence frames.
Architectural Role of Diagrams (The 4+1 View Model)

Diagrams correspond directly to the famous Kruchten 4+1 Architectural View Model:

  • Logical View: Class & Object Diagrams (End-user functionality).
  • Process View: State Machine, Activity, & Sequence Diagrams (Concurrency & performance).
  • Development View: Component & Package Diagrams (Code organization).
  • Physical View: Deployment Diagrams (Hardware execution nodes).
  • Scenarios (+1): Use Case Diagrams (Unifies all four views).

Class Diagram

Static System View, Notation, Multiplicities & Modeling Real-World Domains

Foundational Diagram

Definition and Purpose of Class Diagrams

A Class Diagram is the foundational structural diagram in Object-Oriented Modeling. It provides a static view of the system by modeling the classes that populate the domain, their internal structures (attributes and operations), and the static semantic relationships (associations, generalizations, dependencies) connecting them.

Key Subtopics & Architectural Components

1. The Static View of a System

A class diagram does not capture time, method invocations, or data transformations. Instead, it defines the invariant rules of the universe in which the software operates. It serves three distinct phases:

  • Conceptual Phase: Captures domain vocabulary and business entities without implementation details.
  • Specification / Design Phase: Defines software interfaces, contracts, parameter types, and architectural abstractions.
  • Implementation Phase: Maps directly to source code classes, database relational schemas, or ORM entities.
2. Relationships and Constraints in Class Diagrams

Classes connect through rich semantic relationships:

  • Associations with Multiplicities: Specifies allowable instances (e.g. 1 to 1..*).
  • Role Names: Labels the function a class plays in the association (e.g., employer vs employee).
  • Navigability: Indicated by arrowheads; shows which class maintains a reference to the other.
  • Constraints: Tagged rules such as {ordered}, {unique}, or {xor} governing association links.

Object Diagram

Runtime Snapshots, Object Notation, Attribute Values & Links vs Associations

Instance Snapshot

Meaning of Object Diagram

An Object Diagram (also called an Instance Diagram) represents a static snapshot of a system at a particular moment in runtime execution. While a class diagram models abstract rules and templates, an object diagram portrays the concrete objects that exist in memory, their current attribute values, and the real links instantiated between them.

Key Subtopics & Syntax Rules

1. Object as an Instance of a Class

An object is an entity with concrete state, behavior, and identity:

  • State: Represented by exact values assigned to attributes at that instant (e.g., balance = 5000.50).
  • Identity: Every object is distinct, even if its attribute values match another object.
  • Notation Rule: The name compartment of an object is ALWAYS UNDERLINED.
2. Object Name Syntax Options

In UML, object headers follow three standard conventions (all underlined):

  1. objectName : ClassName — Named object of a known class (e.g., book1 : Book).
  2. : ClassName — Anonymous Object: The object identity is unnamed, but its class type is known.
  3. objectName — An object whose class is either implied or unspecified.
3. Links Between Objects

A Link is an instance of an association. If an association exists between class Book and class Patron, then a runtime link can exist between book1 and johnDoe. Important differences:

  • Links do NOT have multiplicities (multiplicity is a class-level rule). A link simply exists or does not exist.
  • Links connect specific object instances with solid lines.

Terms and Concepts of Class/Object Diagrams

Class, Object, Attribute, Operation, Association, Link, Multiplicity & Constraints

Terminology Master

Core Vocabulary for Structural Modeling

To master structural modeling, you must possess an unambiguous grasp of the ten fundamental terms that form the backbone of both class and object diagrams.

The 10 Essential Concepts Explained

1. Class vs. 2. Object

A Class is an abstract descriptor and classifier that defines a set of features (properties and behavior). An Object is a discrete concrete instance of a class that occupies runtime memory and maintains a unique identity and specific state.

3. Attribute vs. 4. Operation

An Attribute is a named property of a class that describes a range of values that instances may hold. An Operation is the implementation of a service that can be requested from any object of the class to affect behavior or mutate state.

5. Association vs. 6. Link

An Association is a structural relationship between classifiers describing a set of connections among instances. A Link is a specific physical or conceptual connection among objects (a tuple of object references); it is literally an instance of an association.

7. Generalization vs. 8. Aggregation

Generalization is a taxonomic relationship between a general classifier and a specific classifier ("is-a"). Aggregation is a specialized association specifying a whole-part hierarchy ("has-a" or "part-of").

9. Multiplicity & 10. Constraints

Multiplicity defines the allowable cardinality range of instances that can participate in a relationship:

  • 1 or 1..1: Exactly one instance.
  • 0..1: Zero or one (optional).
  • * or 0..*: Zero or many (unbounded).
  • 1..*: At least one, up to many.
  • m..n: Specified range from m to n.

A Constraint is an extension mechanism specifying a condition or proposition that must hold true for the model element, declared within curly braces: {age >= 0}, {ordered}, {frozen}.

Modeling Techniques for Class and Object Diagrams

Noun Extraction, Identifying Responsibilities, Multiplicity Representation & Validation

Engineering Methodology

Step-by-Step Modeling Methodology

How do software architects transform ambiguous english problem statements into rigorous, bug-free UML Class and Object Diagrams? By following a disciplined 7-step engineering pipeline based on the classic Abbott Grammatical Analysis Method.

The 7-Step Modeling Pipeline

Step 1: Identify Classes (Noun Extraction Method)

Analyze the system requirements document and highlight all nouns and noun phrases. Candidate nouns represent candidate classes:

  • Rule: Filter out synonyms, system boundaries, and primitive values (e.g. Customer, Order, Invoice are classes; String, Age are attributes).
Step 2: Identify Attributes and Operations (State vs. Action)
  • Attributes (Adjectives / Possessive Nouns): Properties that describe an object's state (e.g., customer name, order date).
  • Operations (Verbs / Verb Phrases): Actions, requests, or services performed by or on the object (e.g., calculateDiscount(), cancelOrder()).
Step 3: Identify and Categorize Relationships

Examine how entities interact:

  • "A is a B" → Generalization (e.g. SavingsAccount is an Account).
  • "A has a B" (part cannot exist alone) → Composition (e.g. Order has OrderLineItems).
  • "A has a B" (part can exist alone) → Aggregation (e.g. Team has Players).
  • "A works with / references B" → Association (e.g. Customer places Order).
  • "A temporarily uses B" → Dependency (e.g. Order uses PaymentService).
Step 4: Represent Multiplicities Accurately

Ask boundary questions for both directions of the association: "Can a Customer exist with 0 Orders? Yes (0..*). Can an Order exist without a Customer? No (1..1)."

Step 5: Convert Conceptual Model to Formal Class/Object Diagrams

Draw the 3-compartment class boxes, attach association lines, assign role names, and add necessary constraints (e.g. {ordered}).

Step 6: Instantiate Object Diagram Test Snapshots

Create an instance diagram with concrete values to sanity-check corner cases (e.g. what does a customer with zero orders look like? what does a cancelled order link to?).

Step 7: Validating the Diagram (Architectural Checklist)
Validation Check Verification Rule
Completeness Does every use case requirement have supporting classes, attributes, and operations?
Minimality Are there redundant classes, orphan classes with no links, or unused attributes?
Consistency Do role names and navigabilities align with real-world business constraints?
Decoupling Are high-level classes decoupled from volatile implementations via interfaces?

Interaction Architecture

Meaning and Purpose of Collaboration Diagrams

A Collaboration Diagram (officially designated as a Communication Diagram in UML 2.x) is an interaction diagram that models the structural organization of software objects that send and receive messages.

While a Sequence Diagram emphasizes the chronological time order of messages, a Collaboration Diagram emphasizes the spatial layout and structural links among cooperating software objects.

Key Subtopics & Architectural Perspectives

1. Relationships Among Software Objects

Collaboration diagrams portray objects arranged in free-form two-dimensional space. Solid lines represent Links (the runtime conduit through which objects communicate). If no link exists between two objects, they cannot exchange messages.

2. Interactions and Messages

Loop Modeling

Meaning of Iterated Messages in Collaboration

An Iterated Message represents a message that is dispatched repeatedly across a link, either over a collection of target objects or in a loop until a termination guard condition evaluates to false.

UML specifies the asterisk symbol (*) immediately following the sequence number to denote repetition:

Terms and Symbols in Sequence Diagram

Notation Master

Standard Symbols of Sequence Diagrams

To construct semantically accurate sequence diagrams, UML defines seven standardized graphical primitives representing participants, execution control, message types, and object lifecycles.

The Standard Primitives Explained

1. Participants and Class Roles

Rendered as labeled boxes at the top of the diagram: objectName : ClassName.

2. Lifelines

A vertical dashed line extending downward from the participant box. It represents the existence of an object over time during the interaction.

3. Activation / Execution Occurrence (Focus of Control)

A thin vertical rectangle overlaid on top of a lifeline. It denotes the exact period during which the object has the CPU focus of control and is actively performing an operation (either directly or waiting on a nested sub-operation).

4. Types of Messages (Strict UML Arrowhead Rules)
  • Synchronous Call (──▶): Solid line with a solid filled triangular arrowhead. The caller blocks and halts execution until the call finishes.
  • Asynchronous Call (──>): Solid line with an open stick arrowhead. The caller fires the message and immediately resumes execution without waiting.
  • Reply / Return Message (╌╌>): Dashed line with an open stick arrowhead. Carries return data back to the caller.
  • Found Message: Originates from an unknown sender outside the diagram (drawn from a black dot).
  • Lost Message: Sent to an unknown recipient outside the system boundary.
5. Destroying Objects (The Big "X")

When an object is destroyed or garbage-collected during execution, its lifeline terminates with a prominent large "X" symbol, indicating its death.

6. Combined Fragments (Frames)

Rectangular boundary frames with an operator tag in the top-left corner:

  • alt: Conditional branching (equivalent to if-else).
  • opt: Optional execution (equivalent to if without else).
  • loop: Iteration with guard condition [min..max].
  • par: Parallel / concurrent thread execution.

Asynchronous Messages

Non-blocking Invocations, Priority Queues, FIFO Buffering & Multi-priority Scheduling

Concurrent Processing

Meaning of Asynchronous Messages

In distributed, multi-threaded, and reactive systems, an Asynchronous Message allows a sender to dispatch a request or signal and immediately resume its own processing without waiting for the recipient to receive, process, or acknowledge the message.

Message Queues and Priority Handling

1. Asynchronous Message Without Priority (Standard FIFO Queue)

In a standard non-priority setup, incoming asynchronous messages are buffered inside a First-In, First-Out (FIFO) queue:

  • Messages are appended to the rear of the queue as they arrive.
  • The consumer thread pops messages from the front in strict temporal order of arrival.
2. Asynchronous Message With Priority

In real-time and mission-critical systems, certain events (e.g. emergencyHalt(), hardwareFault()) cannot wait behind hundreds of routine requests. Messages carry an explicit priority tag (e.g., High, Normal, Low):

  • High-priority messages jump ahead of normal messages in the queue.
  • A priority queue dispatcher continuously services the highest priority message available.
3. Multiple Priority Queues Architecture

Instead of a single complex sorting heap, modern real-time operating systems and event dispatchers maintain multiple distinct FIFO queues—one dedicated to each priority level (e.g., Critical, High, Standard, Background). The scheduler always drains higher queues before touching lower ones.

Callback Mechanism

Inversion of Control, Registering Interest, Listener Pattern & Event Notification

Design Pattern

Meaning of Callback Mechanism

A Callback is a software mechanism implementing Inversion of Control (IoC). Instead of a client continuously polling a server for long-running task status, the client passes an executable reference (a callback interface or lambda) during registration, and the server invokes that callback when the task completes or an event occurs.

The 3-Phase Callback Lifecycle

1. Phase 1: Registering Interest (Subscription)

The client issues a synchronous message to the service: registerListener(this) or subscribe(callback). The server stores this reference in its internal subscriber collection.

2. Phase 2: Asynchronous Trigger (Background Event)

The client continues with its independent tasks. Concurrently, the server processes the long-running job (e.g., downloading a massive file, waiting on a payment webhook, or listening for hardware sensor interrupts).

3. Phase 3: Callback Message Invocation

Upon event occurrence, the server actively initiates a call back to the client: onTaskCompleted(result). The client handles the result asynchronously.

Activity Diagram

Workflow Architecture

Meaning of Activity Diagram

An Activity Diagram is an advanced, object-oriented flowchart that models the flow of control and computation from activity to activity. It excels at visualizing step-by-step algorithms, multi-department business processes, and concurrent/parallel operations.

Activity Diagram Notations and Components

1. Foundational Nodes
  • Initial State (●): A solid black circle marking the entry point of the workflow.
  • Activity / Action State: A rounded rectangle representing a discrete step of computation.
  • Control Flow: Solid directed arrows showing progression between activities.
  • Decision & Merge (◇): A diamond node with guard conditions (e.g., [isApproved] vs [else]).
  • Final State (◉): A solid circle enclosed inside an outer circle (bullseye) marking termination.
2. Concurrency: Fork and Join Synchronization Bars
Fork Bar (Splitting Concurrency)

A solid thick horizontal or vertical bar with one incoming transition and two or more outgoing parallel flows. Demonstrates concurrent thread execution.

Join Bar (Synchronizing Concurrency)

A solid thick bar with multiple incoming concurrent flows and exactly one outgoing flow. The outgoing flow cannot execute until ALL incoming activities finish.

3. Swimlanes (Activity Partitions)

Vertical or horizontal parallel columns dividing the diagram into distinct organizational departments, actors, or microservices (e.g. Customer, OrderService, Warehouse). Shows exactly who is responsible for each action.

Reactive Lifecycle

Meaning of State Machine Diagram

A State Machine Diagram (or Statechart) models the lifecycle of a single reactive object from creation to destruction. It specifies how an object transitions between discrete states in response to external events, signals, and internal conditions.

State Machine Anatomy & Syntax

1. Core Concepts
  • State: A condition or situation in the life of an object during which it satisfies some condition, performs an activity, or waits for an event. Rendered as a rounded rectangle.
  • Initial State (●): The default state upon object instantiation.
  • Final State (◉): Termination of the object's lifecycle.
  • Transition: A directed relationship between two states indicating movement.
2. Complete Transition Syntax
event-name (parameters) [guard-condition] / action-expression
  • Trigger Event: The occurrence that prompts the transition (e.g. liftReceiver).
  • Guard Condition: A boolean expression enclosed in square brackets [...]; transition occurs only if true.
  • Action: An atomic, uninterruptible calculation executed during the transition (e.g. / playDialTone()).
  • Internal State Activities: entry / action, exit / action, do / ongoingActivity.

Process and Thread

Concurrency Foundations, Active Objects, Context Switching & Architectural Differences

Concurrent Systems

Processes and Threads in Behavioral Modeling

Modern software systems rarely execute on a single linear execution thread. To model real-time responsiveness, multi-core hardware, and distributed microservices, UML integrates the operating system abstractions of Processes and Threads via Active Objects.

Deep Architectural Comparison: Process vs. Thread

1. Foundational Definitions
  • Process: A heavyweight, independent execution unit that owns its own dedicated virtual memory space, file descriptors, and OS security credentials.
  • Thread: A lightweight unit of execution that resides inside a host process, sharing the memory heap, global variables, and open files with its sibling threads.
2. Systematic Comparison Matrix
Criterion Process Thread
Memory Address Space Isolated memory space (safe from corruption by other processes) Shared address space (requires synchronization locks)
Weight & Overhead Heavyweight (expensive creation, destruction, and context switching) Lightweight (cheap creation and fast CPU context switching)
Inter-Communication IPC mechanisms (Sockets, Pipes, Shared Memory, Message Queues) Direct memory reference (Shared pointers, Mutexes, Semaphores)
Crash Impact Failure in one process does not crash other processes An unhandled exception in one thread can terminate the entire process
UML Stereotype <<process>> <<thread>>
3. Active Objects in UML

An Active Object is an object that owns an independent thread of control and can initiate behavior autonomously. In UML, an active class is depicted as a standard class rectangle with double vertical lines on its left and right borders.

Visual Model: Process Address Space vs Multi-Threaded Process Architecture

Events and Signals

Stimuli Triggers, Signal Hierarchies, Call/Time/Change Events & State Transitions

Stimulus Modeling

Meaning of Events and Signals

An Event is the specification of a significant occurrence in time and space that has no duration and can trigger a state transition or dynamic execution. A Signal is an asynchronous package of data transmitted between objects.

The Four Fundamental UML Event Types

1. The 4 Kinds of Events in UML
1. Call Event

Represents the dispatch of an operation on an object. Often synchronous: caller waits for return value.

Syntax: depositFunds(accountNo, amount)

2. Signal Event

Represents the receipt of an asynchronous signal entity. Signals are first-class classifiers adorned with <<signal>>.

Syntax: PowerFailureSignal

3. Time Event

Represents the expiration of a specific time duration or the arrival of a scheduled deadline.

Syntax: after (30 seconds) or at (12:00 AM)

4. Change Event

Represents the satisfaction of a continuous boolean condition.

Syntax: when (temperature > 120°C)

2. Signal Communication and Classifiers

Signals can be structured in inheritance hierarchies. For example, HardwareErrorSignal can generalize into DiskError and MemoryParityError. Subclasses inherit all parameters of parent signals.

Time Diagram

Real-Time Interaction

Meaning of Time Diagram (Timing Diagram)

A Time Diagram (officially Timing Diagram) is an interaction diagram that models the exact change in state or condition of an object along a calibrated, continuous time axis.

While sequence diagrams show the qualitative order of messages, timing diagrams model quantitative durations, response latencies, and clock intervals.

Key Subtopics & Real-Time Utility

1. Key Structural Elements
  • Horizontal Time Axis: Calibrated with explicit time units (microseconds, milliseconds, or clock cycles).
  • Lifeline / State Tracks: Displays discrete state levels (e.g., Idle, Busy, Transmitting) as stepped waveform lines.
  • State Transitions: Stepped transitions rising or falling from one state level to another.
  • Duration Constraints: Mathematical limits (e.g. {t..t+10ms}) specifying strict real-time deadlines.
2. Utility in System Design
Application Area Engineering Importance
Embedded & Automotive Systems Verifies sensor read deadlines and airbag deployment latencies (< 20ms).
Digital Electronics & ASIC Design Models clock jitter, setup/hold times, and bus bus-arbitration protocols.
Distributed Telecommunications Ensures packet timeout retransmission limits and handshake validity windows.

Modular Architecture

Meaning of Package and Package Diagram

A Package is a general-purpose grouping mechanism used to organize UML elements (classes, interfaces, use cases, components) into high-level, manageable, modular namespaces. A Package Diagram depicts the dependencies and hierarchical relationships among these subsystems.

Package Notation and Architectural Dependencies

  • Structuring High-Level Subsystems: Enforces architectural patterns like 3-Tier Layering (UI Layer → Business Logic → Data Access).

Component

Modular Unit

Meaning of Component

A Component is a modular, deployable, and replaceable part of a software system that encapsulates implementation details and exposes a set of external interfaces. It is a physical packaging of logical elements.

An Interface is a named collection of operations that specifies a contract for the services offered by a class or component without dictating its internal implementation. It enforces the Separation of Interface and Implementation.
